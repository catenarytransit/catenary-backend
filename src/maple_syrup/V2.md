# Maple Syrup v2 production storage

Apply both v2 Diesel migrations, then deploy all itinerary readers before deploying
Maple with v2-only writes enabled. The allowlist remains in `maple_syrup_v2.toml`
(`MAPLE_SYRUP_V2_CONFIG` overrides the path; an empty feeds array writes v1).
Maple chooses a timing format once per ingest attempt. For an allowlisted feed it
writes canonical itinerary metadata and both v2 layouts, **without building or
inserting legacy itinerary stop rows**. Other feeds continue to write v1.

## Metadata and identity

`gtfs.itinerary_pattern_meta` is retained for both formats: existing itinerary IDs,
trip IDs, route, direction, shape, timezone, chateau and row count remain
authoritative. `maple_v2_trip_major` is the mapping from the complete
(feed, attempt, itinerary ID) key to the shared structure and dense timing index.
Structural stops are shared only when all non-timing fields match. Both binary
layouts are committed in a transaction after metadata exists and before compressed
trips are written; errors propagate to the ingest caller. Metadata cleanup
cascades to the v2 tables, and chateau reassignment uses the metadata join.

## Readers

- Departure boards, nearby departures and realtime departure consumers use the
  stop-major or trip-major reader as appropriate.
- Single-trip, block, Aspen static lookup and realtime itinerary readers use
  `gtfs.itinerary_pattern_trip_reader`.
- Gentian and Edelweiss response enrichment use `gtfs.itinerary_pattern_gentian`.
  Compiled timetable and RAPTOR formats remain unchanged.
- Globeflower and OSM station ranking use `gtfs.itinerary_pattern_stop_reader`,
  which reads structural stop membership without unpacking timings.

Views select the storage format by the presence of a v2 mapping for the complete
itinerary key, not by the current allowlist. Older v1-only or dual-written attempts
and mixed chateaux remain readable. The v2 payload version and encoding are
unchanged; primary values and sparse exceptions preserve nullable arrival,
departure and interpolated timings. SQL views still expand timing rows where
needed; native compressed-column transfer is outside this change.

## Rollout and rollback

Existing attempts are not rewritten or deleted by these migrations. Reingest
allowlisted feeds (use a feed-scoped forced ingest for unchanged downloads); normal
attempt rotation and cleanup retire the older v1 rows. Do not bump the global
ingestion version just to reprocess these feeds. Verify the new production attempt
before removing previous attempts. Do not revert the v2 schema or deploy a reader
that requires the legacy table while any v2-only attempts are needed. Disabling
the allowlist affects future writes only. To return to an older application,
first reingest affected feeds with v2 disabled or reconstruct legacy rows from the
trip reader and validate full parity.

## Validation

Run `cargo test --lib maple_syrup::v2` and compile all affected binaries.
On a staging database after an allowlisted feed is ingested, execute:

```sh
psql "$DATABASE_URL" -v feed='f-networkrail' -v attempt='YOUR_ATTEMPT_ID' \
  -f tests/sql/maple_v2_production.sql
```

The script asserts zero legacy timing rows, complete metadata-to-v2 coverage,
metadata row counts, and exact parity between the two timing views and structural
stop reader. Also compare against a previous dual-written ingest of identical
input, exercise mixed v1/v2 feeds, loops, missing/interpolated times, dwell,
realtime cancellation and frequency departures, and compile the same Gentian
region before/after. Benchmark production ingest, query latency and disk usage.
No live database or compilation checks were run during patch authoring.
